# P7：连续翻译、增量知识与预算驱动的上下文

日期：2026-10-17。状态：P7.0–P7.5 最小实现及回归已完成；P7.6 已开展真实多窗口、共同前缀与容量验证，仍存在流程阻断和语义退化，未通过完整质量验收。详见 [实施报告](translation-p7-results.md) 与 [使用说明](translation-p7-usage.md)。

本阶段承接 [P6 最小实现](translation-p6-mvp-results.md) 和 [格式 / few-shot 实验](translation-p6-format-fewshot-results.md)。保持当前模型与通用提示策略，集中解决连续运行、状态提交、增量索引、上下文压缩和模型容量适配。P6 的漏检与错误确认仍是已知限制；开展 P7 工程开发不等于 P6 质量验收通过。

## 1. 设计结论与范围

采用“不可变历史底座 + 分支内章节提交 + 按需物化的两级索引 + 可重建会话检查点”。同一连续区间按阅读顺序推进；每次模型调用都能追溯到确切的正文版本、知识版本、可见性政策和预算。

本阶段有六项工作：

1. 将模型上下文上限、输出上限和角色请求预算统一到一个预算计算入口。
2. 用实际 token 预算决定一级 / 二级块边界，替代固定 100/10 章及整除假设。
3. 在独立分支连续翻译，支持停止、恢复、旧章修订和依赖失效。
4. 保存每章工作结果，在二级块闭合或压缩时联合生成摘要与知识增量，并向一级汇总。
5. 保持会话前缀稳定，在明确的检查点压缩历史并重建上下文。
6. 用多个连续窗口比较简单滚动、未压缩会话和分层压缩，分别报告工程结果与语义风险。

索引规划增加一个可选的 `child_min_content_tokens`。默认值为 0，兼容旧布局与运行身份。阈值统计实际可见的日文和对应中文正文 tokens，不含协议及导航开销；没有中文时按日文估计译文膨胀，不读取隐藏参考。启用后，如果全文一级布局会迫使二级块低于阈值，或一级因全文输入预算必须切分，就先独立规划 L2，再按每个二级摘要的保守输入配额规划 L1。计划记录 `selected_layout=summary_rollup` 及 `fallback_reason`，根节点预算标记 `basis=child_summary_rollup`。

最低 token 数是软约束，不能跨可见性缺口、章数上限或硬预算强行合并；无法达到的 L2 标记 `minimum_exception`。可合并的邻接短块先尝试合并。一级汇总只消费其明确成员的二级摘要，保留抽取状态、隔离数量和候选标签。至少两个可用子摘要、计划子节点全部就绪、父节点封闭或显式封存开放尾部时，才物化父概括；抽取缺口不能伪装为父级完整覆盖。实体和事件元信息仍按来源确定性汇集，不让父摘要重新生成事实。

父汇总和抽取都使用原有持久账本、最多三次逻辑任务尝试及实际请求预算检查；恢复复用已保存的响应。实际 prompt 中的历史导航与前驱摘要仍可能超过规划时的预留，届时明确阻断，不静默截断。2026-10-18 的 128k 实验验证了这一边界，详见 [DeepSeek 实验报告](translation-p7-deepseek-results.md)。分卷边界及自动导航压缩留待后续。摘要上卷的语义损失仍需独立评估。

2026-10-18 冻结补充：索引的 2500 字及短概括的 400 字改为软目标。保留正常结束的超长输出、实际长度和警告，不仅为字数重复请求；最终 token 预算仍硬校验。新建运行采用 audit-v6，以实际 FINDING 记录数校准 `zero_findings` 并保留原声明；不把计数校准当作语义审定，也不删除无效意见来伪装零问题。旧 prompt／解析 profile 保留。见 [适应性验证](translation-p7-adaptive-results.md)。

P7 不增加作品专属修正规则、不新增语义审查模型、不扩展 GraphRAG。分卷作为一级节点后续设计；本版只预留边界来源和卷标识。

## 3. 统一模型容量与 token 预算

### 3.1 配置的三种数值

- **模型容量**：`context_window_tokens`、`max_output_tokens`，以及供应方若另有规定的 `max_input_tokens`。这是配置所声明的硬上限。
- **角色请求预算**：翻译、审校、裁决、摘要 / 抽取、压缩各自的 `requested_output_tokens`。它不能超过模型输出上限，也不因模型支持长输出就一律取满。
- **估计误差余量**：`token_inflation_factor` 初始为 **1.05**，加上 `safety_tokens` 固定余量，后者默认 2048。

以下配置已由 `load_settings()` 支持，完整可用示例见 `config/translation-p7.example.toml`。容量示例沿用用户提供的 1,048,576 / 131,072，不将其描述为已经验证的供应方承诺：

```toml
[capacity]
context_window_tokens = 1048576
max_output_tokens = 131072
token_inflation_factor = 1.05
safety_tokens = 2048
# max_input_tokens = ...  # 只有端点存在独立输入上限时填写

[roles.translator]
requested_output_tokens = 16384

[roles.reviewer]
requested_output_tokens = 16384

[roles.adjudicator]
requested_output_tokens = 16384

[roles.indexer]
requested_output_tokens = 32768

[roles.compressor]
requested_output_tokens = 16384

[index]
layout = "adaptive-v1"
parent_max_chapters = 100
child_max_chapters = 10
planning_utilization = 0.80

[sequence]
mode = "working"
n_chapter = 3
n_child = 2
compression_trigger = 0.85
compression_target = 0.65
```

100/10 作为首版可配置的语义规模上限；预算较小时两层均自动缩短，预算增大时可重新接近上限。调高上限允许更长节点，但不会仅因模型有大窗口就扩大抽取范围。现有试验已说明“放得进去”与“提取得准确”是两件事。

角色可以引用同一个模型容量配置，也可以独立配置。容量缺失、非正数、输出预留超过模型上限等情况在调用前报配置错误，不猜测模型名对应的容量。旧运行继续使用原 spec；P7 将容量配置散列写入运行清单。

### 3.2 计算公式

令 `E(M)` 为最终序列化消息的本地估计，包含 system、示例、正文、目录、知识、工具定义及已经获得的工具结果；`C` 为总上下文上限，`O` 为本次实际请求的输出预留，`S` 为固定余量：

```text
safe_input = ceil(alpha * E(M))
safe_input + O + S <= C
safe_input <= max_input_tokens       # 若另有输入上限
0 < O <= model.max_output_tokens
```

`alpha` 默认 1.05，应用于估算输入，不应用于模型容量。输出预算使用实际请求的上限，不以预计正文长度代替。缓存命中部分仍计入输入容量，不能从窗口占用中扣掉。账本的输入预留采用 `safe_input`，同时保存原始估计，避免编译器与执行器重复乘系数。

例如 `C=1,048,576`、`O=32,768`、`S=2,048`：估计输入 930,000 时，总预留为 `976,500+32,768+2,048=1,011,316`，可以发出；估计输入 980,000 时，总预留为 1,063,816，必须缩小输入。

同一规则覆盖索引构建、连续翻译、审校、裁决、修订、增量抽取、压缩、工具续接与格式修复。规划时可以先估计工具返回预算；发送时必须用实际完整请求重新检查，不能只检查最初一轮。

### 3.3 1.05 是先验，不是越界保证

记录 `(模型及端点、tokenizer 版本、消息协议版本、角色)` 下的估计 / 实际输入比值。实际输入使用供应方完整的 prompt/input tokens，缓存 tokens 只作为其中的子项统计。没有可比的 usage 时不校准。

首版采用简单、可复现的只上调策略：

```text
observed_ratio = actual_input_tokens / estimated_input_tokens
alpha_next = max(alpha_current, configured_prior, observed_ratio * 1.02)
```

校准在下一次规划或请求预检生效，生成新的预算修订；不改写历史请求，也不在同一运行中自动下调系数。切换模型 / tokenizer 时使用新的校准档案。极端偏差须记录原因，不能通过把使用率贴近 100% 来抵消余量。

输出侧另记录可见正文与 reasoning 用量。若端点将推理计入输出上限，预留必须包含它；仅请求关闭思考不能代替实际验证。首版保留角色级可配置推理预留，并依据已保存用量设置；未知时不得声称已保证足够的可见输出空间。

实际出现上下文越界时：保存请求和错误，重新计算 / 调整未执行计划；不能原样无限重试。若错误不给实际 token 数，只记录越界并按配置的收缩比例缩小请求，不伪造校准样本。输出 `length` 时优先在输入允许且未超过模型上限的情况下提高输出预留；否则缩小节点。格式错误沿用有界修复，语义疑点不触发无止境扩大窗口。

所有恢复共用逻辑任务的最多三次请求上限和运行总预算。拆分后的子任务可各有自己的上限，但须计入原任务的重规划上限及运行总预算，不能靠不断换任务 ID 重置预算。

## 4. 动态两级索引

### 4.1 节点范围成为显式数据

新 `IndexPlan` 保存有序的节点成员及范围，不再要求父章数整除子章数：

```text
IndexPlan: plan_id, source_manifest_id, visibility_policy_id, planner_version,
           capacity_revision, counter_identity, roots, nodes, excluded_ranges
IndexNode: node_id, parent_id, level, ordered_source_ids,
           start_position, end_position, boundary_reason,
           state(open|sealed), volume_id?, boundary_source
NodeRevision: node_id, covered_source_ids, pair_version_ids,
              summary_id, metadata_commit_id, dependency_ids, budget_report_id,
              source_coverage, extraction_status
```

阅读位置以原始目录顺序为准，番外也占位置。隐藏章 / 保留章留为显式缺口，不重新编号。预算规划不能读取隐藏中文来估计双语大小；没有可用中文时使用原文计数与配置的译文长度预留。未来章节只可用允许的目录信息，未进入可见范围的正文不参与摘要或知识抽取。

`node_id` 绑定布局谱系、层级、父节点与起始章节；确切成员、结束位置及开放 / 封闭状态绑定不可变计划 / 节点修订。读取内容须指定修订，不能只凭 node_id 取得可变的“最新内容”。这样开放尾块可以追加而不改变逻辑节点 ID，旧请求仍保留当时的覆盖范围。

已封闭节点边界冻结。新章节太长时先封闭原尾块，再创建下一块，不把历史节点全部重新切分。主动重分已存在范围时产生新的布局 / 节点身份，并明确旧 / 新范围对应关系；单纯追加只产生新的计划修订。

### 4.2 分块算法

1. 对允许的历史范围按阅读顺序列出候选章节；统计日文、可见中文、引用标签、标题等输入。
2. **先规划 L2 候选**：逐章试装。为父级前情与前驱摘要预留上界，再计入当前完整双语、抽取协议、few-shot 和尾部任务；此时尚未确定父归属，不将候选当作最终抽取请求。加入下一章会超过角色输入软预算、输出估计或章数上限时，在现有章节边界封块。
3. **再规划 L1**：连续装入完整 L2。检查该父块完整双语粗摘要请求的输入 / 输出预算及父章数上限；L1 边界必须与 L2 边界一致，不跨父重复装入章节。
4. 接近预算的多个可行边界之间，可优先使用已有标题中的篇章变化提示；标题只是边界线索，不充当剧情证据。
5. 确定父归属后，用实际背景和最终渲染后的请求复算。索引规划只使用硬预算的 80%，为前驱摘要实际长度、元信息和协议开销预留空间。临界情况下缩短受影响的待建子块或回退一个完整子块，重新校验；不截断正文。
6. 保存每个节点的实际章数、输入预留、输出预留、触发分割原因和保留缺口。

L2 的前驱摘要预算使用将来实际会注入的摘要上限，不能仅以当前空前驱规划。积累超过预留时，在发送前压缩可压缩的前驱说明或缩短待建节点；已经封闭的节点不重分。若背景本身已经放不下，先使用第 7 节的合法短概括，不能假装缩小当前块就能解决。实际前驱版本是抽取请求依赖，父内串行构建，独立父块可并发。

单章本身超过可用输入预算时返回 `oversized_chapter` 及预算报告。P7 首版不自动切开对白或新增章内翻译拼接协议；这一情况与可正常缩短的多章索引块分开处理。

### 4.3 输出限制也会导致分块

完整输入能容纳不代表摘要 + 事件 + 元信息能输出完。规划同时估计摘要上限、字段开销、候选条目上限和推理预留；输出风险过大时缩小 L2，或调整摘要 / 抽取角色的请求预算。

沿用整体摘要最多 2500 字、不设下限；不要求填满最大输出 tokens。字段 / 条目上限只控制任务大小，不能静默删除关键未决事项后宣称完整。发生实际输出截断时，该修订保持不完整，按第 3 节处理。

分块长度与摘要长度是两个配置。降低模型输出上限时，先重算摘要、元信息能否共存；低于最低任务预算则显式报错，不能单纯缩短输入后仍请求一个不可能完成的输出。

### 4.4 旧索引和将来的分卷

已有 100/10 索引可作为 `legacy-fixed-v1` 计划整体导入：合法的封闭节点不为采用新规划器而强制重建，后续待建范围使用新规划。范围、双语版本和可见性完全匹配才可复用摘要；只有部分交集时不能把旧摘要改个范围标签继续使用。

更换消费模型时，重新计算摘要注入预算，允许复用仍合法的旧摘要内容。摘要的原生成模型 / tokenizer 身份保留作溯源，不把“消费模型 tokenizer 改了”等同于“语义产物已失效”；现有严格绑定需通过版本化读取适配器调整。

预留 `boundary_source=fixed|token_budget|title_hint|volume`、`volume_id`。未来“分卷=L1”可成为另一布局策略；超长卷可能需要多次构建再汇总，不能把卷边界和单次请求边界混为一谈。本阶段不识别卷、不重排现有语料。

## 5. 连续翻译分支与提交

### 5.1 工作译文与正式接受

P6 仍有语义漏检，若每章必须达到正式接受条件才继续，当前模型难以支持有意义的连续试验。P7 因此定义两种模式，默认开发实验使用 `working`：

| 模式 | 可供下一章使用的文本 | 未解决语义疑点 | 对正式接受的影响 |
| --- | --- | --- | --- |
| `working` | 当前分支已提交的最终工作版本，或合法既有译文 | 保留问题、质量标签和证据；仅作为本分支未审前文 | 不创建 `translation-acceptance`，不进入正式输出或 K0 |
| `accepted_only` | 通过现有接受流程的确切版本 | 需要原接受策略完成处置，否则停止 | 沿用既有显式接受语义 |

工作提交要求：完整非截断的生成结果、可重现的来源及段落覆盖、无机械硬错误、预定的审校 / 裁决步骤有完整协议。已确认且尚未处理的严重问题阻断；未决语义问题可带标签继续。草稿、中间修订、格式不完整响应不能进入下一章正文。

这种许可只服务于开发实验，不提高候选知识权威。程序上的零发现、可接受状态及 working 提交都不能作为质量通过证明。没有引入每章必须人工批准的新流程。

### 5.2 分支隔离和可见性

首版每条分支使用独立的 `NarrativeStore` SQLite 文件；共享历史数据只读，导入不可变对象时保留来源清单。这样复用现有以 `source_id` 为键的接受表时不会发生不同试验互相覆盖，无需一次迁移全项目数据库。

`SequenceRun` 绑定：语料版本、连续目标区间、分支模式、K0 / 历史索引快照、模型与角色配置、prompt 版本、预算策略、总请求预算和初始检查点。一个分支只有一个写入者；多个独立分支可以并发。

验证时一次隐藏整个连续窗口的原有中文，而不是逐章解除隐藏。下一章只允许使用：

- 窗口前允许的历史原文 / 译文；
- 本分支已经提交且早于当前目标的生成版本；
- 基于上述来源构建的合法摘要和知识；
- 当前目标原文。

新增 `SequenceNarrativeView` 对 `corpus_reference`、`generated_working`、`generated_accepted` 分别检查。不能为读取生成前章而解除该章原有中文的隐藏；也不能用另一分支同章译文或包含未来窗口内容的父摘要。仅有相同章号不构成可复用条件。

### 5.3 章节状态机与原子提交

```text
planned → context_ready → generated → review_finished → commit_prepared → committed
                     ↘ request_failed / budget_blocked / review_blocked
```

一个 `ChapterCommit` 保存最终文本版本、父提交、实际上下文 ID、审校结果、未决问题、增量状态和来源依赖。提交前可准备不可变对象；一次 SQLite 事务同时更新分支头、章节清单、知识工作集头及待物化索引任务，校验 `expected_head` 和幂等键。

原响应先落盘，远程调用不置于数据库事务内。提交后的章节不能因进程重启再次接受 / 提交；已落盘且可验证的响应在恢复时零模型调用。响应未保存的超时只能标记远端结果未知，沿用有界重试，不承诺远程请求严格执行一次。

首版知识工作集使用本分支 `NarrativeStore` 内的不可变对象和 P6 提交；K0 在 P4 KnowledgeBase 中只读。无需跨两个 SQLite 原子写入。后续若将候选发布到共享知识库，再复用 outbox，不阻塞本分支连续实验。

## 6. 知识增量挂载在索引节点

### 6.1 每章记录，按块物化

每章提交先保存完整原文、最终工作译文、审校发现、未决事项、已有约定的字面使用位置及依赖。单纯同段出现的日文词和中文词不自动认定为对应译名。此步骤不要求额外 LLM 请求，也不在每章重新生成 L1。

二级块闭合，或即将把其原文移出会话时，才对该块全部合法双语联合构建：

- 剧情摘要及事件、原因、结果；
- 人物 / 作品专名描述与实际译法；
- P6 时序、视角、知情状态、歧义及未决问题。

抽取继续携带允许的父级前情和同父前驱 L2 摘要；新事实以日文为依据，中文仅证明本分支实际用了什么表达。新译名标记 `provisional_rendering`，不会因连续使用次数增加自动变成已审规范。

尚未物化的尾部章节以完整双语留在会话；默认最近 3 章是最低保留范围，而不是允许把第 4 章立即删除。容量压力可以提前封闭一个少于 10 章的 L2。若抽取失败，保存 `partial/summary_only/missing` 与缺口；可保持全文继续，无法同时保留全文又容纳下一章时停止，不能用失败摘要替换全文。

### 6.2 父级与全文元信息

L2 修订挂载摘要、候选知识及完整来源。L1 的元信息通过确定性汇总更新：保留子记录、命名空间化 ID、冲突、来源与候选状态，不用 LLM 强行合并实体身份。

已有历史 L1 概括可保持不变，新增的子详情与元信息作为修订追加。新翻译形成的开放 L1 使用“已覆盖前缀概括 + 新 L2 摘要 / 原文尾部”，明确实际覆盖到哪一章。到 L1 封闭或检查点需要时，再从当前 L2 产物生成一次粗概括；其输入上限与缺失来源须可追溯，必要时取回原文。

父级概括可以压缩子摘要，但重要约定、未决事项和结构化状态独立保留，不只寄存在概括文字中。禁止以“上一版压缩摘要 + 本章增补”无限递归地替代全部来源。

全文元信息是候选与用法的版本化目录，不要求全部塞入 prompt。核心约定、当前相关实体、适用时间及相关冲突进入工作集，其余可通过已有查证工具读取。未记录“知道”不能变成“确定不知道”，人物声称不能因汇总而变成叙述事实。

冻结底座仅意味着输入版本固定，候选的原有质量标签仍保留。若没有已审核心约定，已审集合可以为空；P7 不以补建一套全书已审知识卡为启动条件。

### 6.3 修订与撤销

修正早章时创建新文本 / 增量版本，保留旧版。依赖它的节点摘要、知识快照、检查点及后续译文标记 `stale`。因为连续会话有顺序依赖，首版保守地将该章之后的本分支后缀列为待重审；不尝试判断每个词是否真的受影响。

默认从最后一个仍有效的前驱提交派生新分支继续，旧分支可审阅。不得继续使用带失效依赖的缓存前缀；也不把历史结果直接删除或原地改名。

## 7. 会话布局与上下文压缩

### 7.1 一段会话内只追加

检查点后的翻译请求布局：

```text
system：稳定翻译任务、资料边界、输出协议
user：冻结核心约定与本检查点的知识工作集
user：历史 L1 概括、近 L2 详情、未决事项与查证目录
user：检查点时最近 N_chapter 章完整双语
user：第 k 章原文与本章约束
assistant：第 k 章最终已提交的工作译文
user：必要的增量约定 / 问题标记 + 第 k+1 章原文与任务
assistant：第 k+1 章最终已提交的工作译文
……
```

审校、裁决、抽取的完整对话独立保存，只把最终版本和与续译相关的增量放入翻译会话。若修订改变上一章回答，下一次请求使用最终版；该位置之后的缓存前缀自然失效，不能为了缓存保留错误草稿。

在同一检查点周期内，已经注入的概括与工作集文本保持稳定，新增约定放尾部。若新约定推翻固定核心内容，立即重建检查点，不能靠一串互相矛盾的追加说明解决。

这里的“缓存友好”是消息前缀可复用，不是本地持有或迁移模型 KV。完整消息仍保存并发送；缓存命中只依据供应方实际 usage 字段报告，缺失则记为不可观测。

### 7.2 触发与重建步骤

在准备下一章时计算该章完整请求。安全输入预计超过可用输入预算的 85% 时尝试压缩，目标降到 65%；跨 L1、修改核心约定或依赖失效也触发检查点。阈值基于扣除本次输出预留和固定余量后的输入预算，硬预算始终另行核验。

压缩顺序：

1. 冻结当前分支头，检查已提交文本与待物化块；需要移出全文的范围先生成 / 读取合法 L2。
2. 保留最近 `N_chapter=3` 章完整双语、最近 `N_child=2` 个二级节点摘要 / 详情，以及尚未物化的全文尾部。
3. 更远的已覆盖范围使用对应 L1 概括；若当前 L1 只有开放前缀，不用未来章内容补齐。
4. 确定性保留核心译名、仍适用的约定、相关时间 / 视角标记、未决问题及冲突，附原始 ID 和证据入口。
5. 编译新消息、预算报告与逐范围覆盖清单，写入不可变检查点；只有来源合法、必需项保存且预算通过才切换会话。

范围清单记录某段前文由 `full_pair / L2 / L1 / explicit_gap` 哪种形式覆盖。模型声明“都总结了”不代替范围检查；范围覆盖也不等于语义无损。原始正文与所有旧摘要继续保留，可按需取回。

### 7.3 小窗口下，远块摘要本身也可能超预算

缩小索引块会增加 L1 节点数，不能只解决构建请求就假定翻译 prompt 一定放得下。检查点编译器先扣除近章、目标、核心约定和输出预算，将剩余预算分配给远块概括。

必要时为 L1 建立短概括变体 `compact_overview`，每条仍对应原节点、确切版本及完整可见范围。它从规范 L1 / L2 产物重新生成，不从上一版短概括反复压缩；重要结构化约定与未决事项仍独立保留。短概括是有损视图，不能替代底层知识。

所有远块仍需有表示，不静默改为 top-k 检索或只放最近几个根。若最小范围表示、必需约定和近章全文都放不下，返回 `minimum_context_does_not_fit`，报告各部分占用。首版不自动降低 N_chapter / N_child，也不暗中创建第三层摘要；扩大容量或显式更改配置后生成新计划。

## 8. 检查点、请求与可观测性

`Checkpoint` 至少保存：分支头、下一章、所选文本 / 节点 / 知识版本、完整可见性政策、原始消息或其不可变对象引用、完整来源覆盖清单、未决事项清单、预算修订、压缩输入和输出、prompt / 模型配置身份。

恢复时验证所有依赖和配置，直接重建确切消息，不重新让模型写一次摘要。已经提交的章节和已经完成的物化任务复用原产物。更换模型、窗口配置或 prompt 形成新运行分支；可复用合法的原文、译文和知识内容，不复用隐式会话状态。

每次请求记录估计输入、安全输入、实际输入、输出上限、实际输出、reasoning / cached tokens（若有）、重试序号、finish_reason、费用是否可观测。每个检查点另报压缩前后大小、保留范围、短概括数量、压缩调用量和总成本；不能只展示压缩后的单次翻译成本。

逻辑提交使用幂等键；模型请求、响应保存、工作提交、节点物化和检查点切换分别设置故障注入点。处于 `commit_prepared` 的孤立对象可复用，但不能自动成为新的分支头。

## 9. 对外 API 与模块安排

以下为拟议 Python API，不先开发 HTTP 服务。读取与规划函数不隐含模型调用；生成 / 物化函数显式接收 provider 和共享总预算。

| API | 输入 / 输出与职责 |
| --- | --- |
| `plan_request(messages, model_capacity, role_budget, calibration)` | 返回 `BudgetReport`：是否适配、分项预算、所用系数、剩余量、失败原因 |
| `observe_usage(budget_report, usage)` | 保存可比的实际用量，产生下一预算修订 |
| `plan_adaptive_index(view, index_spec, role_budget, existing_plan=None)` | 返回只读 `IndexPlan`；冻结旧封闭边界，规划待建范围 |
| `materialize_node(run, node_id, provider)` | 按计划联合生成摘要 / 候选知识，返回不可变 `NodeRevision` |
| `create_sequence(spec, frozen_inputs)` | 创建隔离分支和运行清单，不调用模型 |
| `plan_next(run_id)` | 返回目标、上下文、预算及先决物化任务，不自动执行付费任务 |
| `advance_sequence(run_id, stop_after=None)` | 执行已配置的生成、审校、有限修订、增量准备和工作提交 |
| `commit_chapter(run_id, prepared_id, expected_head, idempotency_key)` | 同库原子提交文本、知识工作集头和待物化任务 |
| `compile_sequence_context(run_id, target_id)` | 输出实际完整消息、来源覆盖及预算 |
| `plan_checkpoint(run_id)` / `materialize_checkpoint(plan_id, provider)` | 先规划缺少的摘要，再有界生成并切换到可验证检查点 |
| `resume_sequence(run_id)` | 校验并恢复；已有合法结果不重新调用 |
| `fork_from_commit(run_id, commit_id, overrides)` | 回滚 / 更换配置后派生分支，旧结果保留 |
| `explain_context(run_id, target_id)` | 导出完整输入、知识来源、增量和压缩替换关系 |

建议按需要增加 `translation/budget.py`、`translation/narrative/partition.py` 和 `translation/sequence/`，后者包含状态 / 提交、分支视图、会话、检查点和执行入口。保留已有 summary / state / review 模块的职责，不复制一套 P5/P6 实现。

CLI 拟为 `python -m translation.sequence plan / run / status / resume / checkpoint / fork / explain`，全部命令绑定运行清单；`plan` 和 `explain` 为本地操作。开发阶段先交付 Python API，再增加薄 CLI。

## 11. 验证方案与验收口径

### 11.1 必须通过的工程场景

1. 同一语料分别配置 1M、128K、64K 总窗口及不同输出上限，验证两级边界、最终请求和输出预留都受约束。较小窗口先做离线 / mock，不假装换成另一真实模型。
2. 构造估计低于实际 8% 的 usage，确认初始 1.05 不能被当作保证，下一预算修订上调并收缩待发请求。
3. 工具结果使输入增加、长 reasoning 使输出截断、无 usage、无本地 tokenizer、单章过长等情况有明确结果，不静默丢资料。
4. 连续隐藏整个验证区间的参考译文，检验生成前章可读而原参考仍不可读；跨分支版本、未来节点和失效摘要均不能进入 prompt。
5. 在响应保存后、工作提交前、提交后物化前、检查点生成后切换前中断；恢复后头版本、已提交文本、知识与待执行任务相同。
6. 同一幂等键重放不重复提交；冲突头拒绝写入；未知远端结果保留预算。正式 accepted 与 working 状态不能混用。
7. 压缩前后稳定 ID 的核心约定、相关冲突与未决事项不丢失、不升权；已被新近正文推翻的状态不继续当作当前事实。
8. 修改早章后，所有依赖它的摘要和检查点失效，后缀标记待重审；旧运行仍可查看。

### 11.2 真实试验分两步

先进行三个窗口各 3 章的串行冒烟，验证工作分支、增量及真实请求预算。窗口从既有开发范围筛选：一个包含时间线 / 人物知识变化，一个包含多人对白 / 称谓，一个位于较晚位置；可优先检查 610、701、1200 附近，但需先核对保留集、对齐质量和可见来源后冻结实际起止章，不直接把这些章号当作已批准范围。

随后每个窗口扩展到至少跨越两个实际 L2 边界，并至少触发一次压缩；其中一个窗口应跨 L1 边界。窗口长度根据动态计划确定，预计 12–25 章，不能为了凑章数解除任何保留集限制。

比较三种上下文策略，使用相同模型、隐藏范围、初始知识、近章下限、P5 审校策略及增量产物协议：

| 组 | 上下文策略 | 用途 |
| --- | --- | --- |
| R | 每章重新编译：固定历史概括 + 最近 N 章 + 当前知识工作集，不保留更长会话 | 简单滚动基线 |
| U | 相同初始底座，累计追加所有已提交章，暂不压缩 | 未压缩参照；超预算时如实停止，不暗中裁切 |
| H | 相同底座，累计追加并按 P7 检查点重建分层上下文 | P7 主方案 |

先对一段冻结的共同前缀做 U/H 配对实验：前章译文、知识和原文完全相同，仅改变上下文表达，评估压缩影响。随后运行 R/U/H 各自的连续分支，评价累积漂移；这时各组后续输入会因各自译文变化而不同，不能将差异全归因于一次压缩。

正常 1M 配置下若没有自然压缩，额外降低**运行输入软预算**进行压力试验，保留真实模型硬容量与输出预留；将这组结果单列，不能宣称已经验证另一小窗口模型。

人工复核点在生成前冻结，至少包括：首次译名与后续一致性、回忆 / 当前状态区别、知情范围、未决事项保留、角色误归属、漏译 / 增义，以及压缩后新增的错误确定性。已有 688 叫声误判等可作为通用审查回归点，不写进生产 prompt 变成作品特定答案。

### 11.3 指标与预算

报告工程指标：完成 / 阻断章节数、重试与回退、重复提交、恢复新增调用、估计 / 实际 token 偏差、压缩次数、来源覆盖、真实缓存字段、全流程调用量和 token 用量。

报告质量指标：正确修复、误报、漏检、译名漂移、时序 / 知情错误、未决项消失、新增严重错误及无法判断项。没有完整可靠标注时不制造精确的准确率 / 召回率，也不把模型自评算作人工结论。

真实实验在 `plan` 阶段按“章数 × 各角色最大调用数 + 索引 / 压缩请求 + 共享重试上限”列出最坏请求数与输出预留，并估算输入。总预算不足则缩短试验，不在运行中无限追加；实际执行预算由后续实施时的冻结运行清单确定。

P7 工程验收要求第 11.1 节场景通过、真实多章流程可运行且可解释地恢复。质量结论单列：压缩导致明显新错误或知识污染时，不能宣布达到质量验收；仍可保留可选功能及明确限制。所有工作译文保持实验状态，P8 的独立质量评测与正式导出继续单列。

## 12. 本轮产物

已交付统一预算、动态两级规划、连续工作分支、双语增量抽取、稳定会话、检查点、恢复及 CLI。实际 Python 签名和命令以 [使用说明](translation-p7-usage.md) 为准：例如 `materialize_node` 的首版批处理入口为 `materialize_pending()`，检查点规划／执行为 `plan_checkpoint()/checkpoint()`。
