# P7 DeepSeek 复测与二级摘要上卷

日期：2026-10-18。代码已实现最低 L2 正文预算及 L2→L1 摘要回退；真实模型表现为：一个已知否定错译得到改善，但连续审校仍被矛盾输出阻断，局部 L1 汇总也在三次尝试后仍超出长度限制。因此没有把本轮结果标记为 P7 翻译质量验收通过。

后续同日已把摘要长度改为软目标，并新增 audit-v6 计数容错及 few-shot，见 [适应性处理与版本冻结](translation-p7-adaptive-results.md)。下文保留原严格版本的观测，不追溯改写旧实验失败结论。

实验根目录：`artifacts/translation/tenken-cache-clean/verification/p7-deepseek-flash-20261018/`。旧 GLM 产物与数据库保持原样，本轮没有新增 git commit，也没有修改本地密钥。

## 1. 运行条件

模型和密钥从现有配置读取。实际端点为本地网关 `http://localhost:9317/v1`，模型名 `deepseek-flash`。网关 `/models` 宣告输入上限 1,048,576、输出上限 393,216 tokens；这只是网关元数据，不能独立证明背后模型身份或供应方能力。本轮以更保守的“输入加预留输出不超过 1,048,576”规划。

`provenance.json` 保存无密钥能力信息及 tokenizer 来源、SHA256；使用 DeepSeek 发布的 tokenizer 文件。其配置文件中的 `model_max_length=16384` 不作为本模型能力上限。聊天封装开销仍是估计值，先乘 1.05，实际 usage 按角色校准。

provider 自动重试关闭，逻辑任务最多三次，`thinking=false`、temperature 0、直接连接、不使用环境代理。本地一跳是 loopback HTTP，没有 TLS；早期捕获里 `tls_verification=true` 的实际传输标签不准确，已补说明，新捕获按 HTTP 记录。配置中 HTTP 客户端的 TLS 验证选项仍保留，其值不证明 HTTP 使用了 TLS，也不证明网关上游的连接方式。

128k/256k 只是受限容量情景，不是当前网关宣告的容量。连续小实验仍沿用 L1=9、L2=3 的压力布局，不能冒充标准 100/10 长窗口实验。新实验 indexer 预留 32768，旧 GLM 连续实验是 16384；严格相同消息的翻译对照另见第 3 节。

## 2. 连续翻译：模型换了，审校仍未跑通

复用旧 1200 窗口的冻结输入，只取前四个目标；目标中文继续隐藏，每个分支使用独立 SQLite。表中章号为 `main` 阅读编号，不能与物理 source ID 混用。

| 分支 | 最低 L2 正文 tokens | 工作提交 | 物理请求 | 阻断位置及原因 |
| --- | ---: | ---: | ---: | --- |
| U-baseline-rerun | 0 | 1 | 7 | main:1201，FINDING 与零问题声明冲突 |
| H-baseline | 0 | 2 | 16 | main:1202，修订后仍有模型确认的 major 问题 |
| H-summary-rollup | 3000 | 0 | 3 | main:1200，FINDING 与零问题声明冲突 |

三分支共 26 请求，输入 2,670,805，输出 23,494，合计 2,694,299 tokens；缓存命中输入 1,988,096，未命中 682,709。没有网络失败，正式接受数为 0。`working` 提交数不能作为翻译准确率。

**这三个连续流程都没有走到真实 L2 抽取。** 因此不能用提交数量的差异评价新索引回退的效果；后章还受到此前模型生成译文的影响。分支名称中的 `rerun` 是本轮已存在的冻结名称，runner 已改为显式选择分支，禁止默认创建新的等价分支绕过失败。

观察到三类问题：

1. H-summary-rollup 生成一个 major FINDING，却声明 `zero_findings: yes`；U 第二章把“没有实质差异、无需修改”的内容写成 FINDING，同时声明零问题。解析器均以 `finding_count_declaration_conflict` 阻断，不能把这种输出视为正常零发现。
2. H 第三章最终审校生成 12 条 FINDING，其中 11 条自己说“无实质差异／无需修改”，裁决均 dismissed。记录数明显受输出协议的误用污染，不等于发现了 12 个错误。
3. 剩余 f1 被 confirmed，但修复建议互相矛盾。原文为「ほとんどの荷物は一時的に目を覚ましたフラン――に見せかけて俺が収納したし」。修订稿写“大部分行李都由我假扮成暂时醒来的芙兰收进了收纳空间”。审校说“我”不该被写成假扮芙兰的人，却建议“我假装成暂时醒来的芙兰……”或“我让芙兰装作暂时醒来……”。前者延续了它指责的问题，后者又增加了安排芙兰行动的解释。

f1 的原文优先复核方向应是表达“表面上由暂时醒来的芙兰收纳，实际上是我收起来”，避免自行增加变身或让芙兰表演的情节。这是人工分析候选，没有写回测试输入，也没有当作模型已正确修复的证据。`confirmed` 只能说明裁决模型做了该判断。

逐分支 `http/` 保存每次完整模型请求和响应，`io/` 保存实际翻译 prompt、原始草稿和工作提交。`diagnostics.json` 另导出全部版本、审校、裁决与账本，包括被阻断后的修订稿，避免只展示初稿。`evaluation/main-1200/comparison.html` 等提供原文、参考中文及分支版本并排对照；参考中文仅在各分支停止并冻结输出后读取。

## 3. 严格相同 prompt：已知新增否定错误没有重现

为隔离模型变量，直接复用旧 `paired-1200-prefix4/{U,H}/context.json` 中的完整 `messages`，每组只调用新模型一次，max_tokens=8192、temperature=0，不运行审校、不提交。它们保留同一组旧的前四章译文及知识候选；与第 2 节的新连续译文分支不同。

目标 `main:1204`，对应片段「魔術の多重起動をしながら」。

| 模型 / 上下文 | 输出片段 |
| --- | --- |
| GLM / U | 一边多重启动魔术 |
| GLM / H | 不进行魔术多重启动的同时 |
| DeepSeek / U | 一边多重启动魔术、一边持续回避敌人的攻击 |
| DeepSeek / H | 一边多重启动魔术、一边持续闪避敌人的攻击 |

新模型两次都没有新增否定，支持“该例与模型选择有关”的判断。每组只有一次样本，不能据此得出整章准确率、整体模型排名或压缩无损结论。输入相同由消息数组逐项相等及哈希检查验证，不只是同章或相近 prompt。

两次请求合计输入 248,931，输出 2,572，总计 251,503 tokens。本轮两次均未报告缓存命中。完整上下文、prompt、输出及六栏对照见 `paired-exact-prompt/`；消息仍未包含目标中文参考。

## 4. 新分块逻辑与离线容量结果

新配置：

```toml
[index]
parent_max_chapters = 100
child_max_chapters = 10
child_min_content_tokens = 32768
parent_summary_input_tokens_per_child = 8192
```

`child_min_content_tokens` 统计可见日中正文 tokens，0 时保留旧规划和运行身份。启用后，当全文父级预算导致切分或 L2 低于软下限，独立规划 L2，再以其摘要输入预算规划 L1；不是让二级节点继续随一级全文窗口无限缩小。L2 仍保存双语全文、段落引用和候选知识，父元信息确定性保留子来源；L1 概括才由模型再次汇总。

最低大小让位于可见性、章数上限及硬预算，短块不能无条件合并。节点记录 `minimum_exception`、布局及预算依据。实际完整消息再次预检，估计规划通过不保证所有导航摘要都能塞入请求。

对同一批合法冻结历史 1063 章离线规划，模型调用 0：

| 模拟上下文 | L2 最低 tokens | 布局 | L1 数 | L2 数 | 最大 L1 章数 |
| --- | ---: | --- | ---: | ---: | ---: |
| 1M | 0 | full_source | 42 | 128 | 100 |
| 256k | 0 | full_source | 51 | 128 | 54 |
| 128k | 0 | full_source | 86 | 128 | 21 |
| 256k | 32768 | summary_rollup | 42 | 128 | 100 |
| 128k | 32768 | summary_rollup | 45 | 128 | 80 |

计划中全部节点通过其估计预算。L2 最大均为 10 章，因此这批数据并未证明小窗口一定把 L2 退化成一章；它实际证明的是摘要上卷能保留更大的 L1 范围。最短 L2 为 2453 tokens，设置阈值后仍有 82 个短块例外；缺口和章数上限不能跨越。L1 数量也受冻结历史缺口影响，不是简单的 1063÷100。

旧 GLM 离线脚本 `offline_p7_capacity.py` 继续使用旧 tokenizer 和原情景；新脚本为 `offline_p7_deepseek_capacity.py`，写入独立目录，未覆盖旧实验产物。

## 5. 真实 128k 局部抽取：L2 可用，L1 长度遵循失败

从已披露历史中选连续阅读位置 1056–1085，共 30 章及合法配对中文，规划一个 L1、三个十章 L2。不伪造工作提交、不越过审校门槛，仅复用正式 `joint_messages`、`ExtractionRecovery`、解析器与父概括代码。

首次携带全部已有 L1 导航时，估计输入 125,495，乘先验后 131,770，再加输出预留 32768 与余量，总预留 166,586 > 131,072。产生 `context_budget`，**未发送任何请求**。诊断保留在 `rollup-probe-128k/`。这揭示了后续还需解决的导航开销，不能靠调整正文节点大小自动消除。

第二个独立探针明确只携带最近一个已披露 L1 导航；不是暗中修改生产分支的全部历史策略。同父 L2 顺序执行，后块携带前驱摘要。结果在 `rollup-probe-128k-near-history/`：

| L2 | 摘要字符 | 接受的 ENTITY / EVENT / TEMPORAL | 隔离记录 | 状态 |
| --- | ---: | --- | ---: | --- |
| 1 | 1691 | 138 / 26 / 23 | 12 | partial |
| 2 | 818 | 29 / 21 / 20 | 1 | partial |
| 3 | 707 | 28 / 36 / 8 | 2 | partial |

三个块各一次请求，正常结束，无截断或协议恢复调用。15 条记录的结构问题包括实体原名／译法不在所引段落，以及空证据；隔离不等于判断整条知识为假，接受也只证明满足结构检查。

第一个块明显存在实体噪声：接受内容包括普通动作／通用词，以及多次重复的「魔獣使い」。摘要还有“沿海南下北上”这样的方向表达。长输出并不自动产生高质量知识；这些产物全部保持 `candidate_unreviewed`，没有晋升成固定约定。

L1 仅使用三个 L2 摘要和质量状态汇总，首次输出 3631 字符，超过 2500 上限。为此增加同一逻辑任务内的有界缩写恢复，原响应完整保存；两次恢复分别为 2849、2844 字符，仍超限，最终 `invalid_summary`。三次均正常 `stop`，不是 JSON 解析错误、输出 token 截断或网络问题；最后一次输入也只有 5550 tokens，不能全部归因于超长上下文。

因此本探针有三个可追溯 L2，**没有合规的活动 L1 概括**。三份 L1 原输出保存在 `L1-attempt-1.txt` 等，可供人工阅读，但没有为了通过实验而放宽长度、截取尾部、重置重试或创建替代任务。再次运行探针只复用保存结果，新增调用为 0。

六请求合计输入 161,267，输出 42,167，总计 203,434 tokens。包括连续实验和相同 prompt 重放，本报告主实验共 34 次、3,149,236 tokens；少量连通性探测另计，不并入这些分支账本。

## 6. 工程验证与结论边界

新增回归覆盖默认布局兼容、阈值回退、一级全文超预算、封闭节点恢复时布局保持、父汇总持久化、缺失子块不得伪装完整父覆盖、长度重试及三次耗尽后零调用恢复。最终 `python -m pytest -q tests/translation` 为 **382 passed**，10 条既有第三方依赖警告。`compileall` 与本轮相关目录的 `git diff --check` 通过；用户已有爬虫改动保留。

本轮区分了三个结论：翻译模型在一个已知错误上改善；最低 L2 预算及摘要上卷在规划和持久恢复层面已实现；当前模型仍不能稳定完成连续审校及受长度约束的父概括。真实长程压缩收益与全流程翻译质量尚未验收。自动压缩历史导航、实体去重／筛选、分卷边界尚未实施，不以本次局部探针冒充其完成。

复现入口：


`report/export/summarize` 不调用模型；探针完成或耗尽后恢复为零调用。不要删除数据库、冻结清单或 `sent.json` 后冒充同一次实验。新模型、容量、阈值或 tokenizer 应创建独立运行身份。
