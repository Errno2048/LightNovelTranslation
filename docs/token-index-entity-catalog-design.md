# Token 分块、实体合并与核心目录

> **Legacy 文档**：本文描述旧 `sequence` 索引。main 的新架构见 [refactor-architecture-design.md](refactor-architecture-design.md)；旧实现位于 `legacy-sequence` 分支。

本设计用于新建索引和任务。旧任务保留冻结的配置、节点边界、请求和响应；不在恢复时改变其语义。

## 1. 目标和边界

三个独立步骤仍为：选择参考模式、建立索引、翻译。独立版本索引、任务历史索引和译后增量索引共用 token 分块规则，但各自保留输入身份、可见范围和存储。跨版本中文只支持文风和译名候选，不能覆盖日文事实。

默认 L1 最少 30 章、最多 100 章，目标 10 个 L2。预检按每个 L2 至少 3 章估计 L1 的最小有用规模；正式划分 L2 按 token 平衡，允许单章很长时不足 3 章。这里的 30 是完整 L1 的硬下限，不是只要 token 太多就可以缩小的目标。参数可以显式修改，诊断必须说明实际采用值。

不足下限的整部作品、真实卷界或末尾余量允许成为带 `short_range` 标记的节点；增量不足下限的尾部保持 open。不能为满足下限跨越输入缺口或读取尚未翻译的未来正文。

## 2. 统一的本地规划

1. 估算每章标题、正文、段落引用包装和已允许的中文参考；未知的新译文只按源文估计膨胀预留，不读取答案。
2. 输入上限扣除角色最大输出、模型 safety、协议和前驱导航预留，再乘规划利用率。每次输入估算乘 `token_inflation_factor`（默认 1.05）；实际请求还使用完整消息预算检查和已有校准。
3. 对连续可见区间，先以 `max(1, round(n / 30))` 个预期 L1 按 token 权重划分，保留章节完整性并约束完整 L1 的最小章数。用于确认最小规模是否可直接摘要。
4. 可行后尽量扩展 L1 到上下文可承受的最大范围，且不超过 100 章。按 token 权重平衡相邻节点，避免只按相同章数切割；小余量优先回并或重平衡，无法消除时显式标注末尾例外。
5. 每个 L1 内以 token 权重规划约 10 个非空 L2，正式 L2 不设 3 章硬下限。单章不能装入时返回 `oversized_chapter`。
6. 默认 `parent_build_mode = "direct"`。最小 L1 不能直接装入时，计划给出 `index_capacity_decision_required`、章节范围、预算和可选操作。不得自动构建所有 L2。调用方可显式选择 `child_summary_rollup` 或 `direct_then_rollup` 后新建计划；格式错误、超时和语义不完整不是容量回退依据。
7. 增量使用同一 planner，已封口 L1 和 L2 保持稳定，只重新规划 open 尾部；重新规划不改写旧节点修订。

`child_max_chapters/child_target_tokens/child_min_content_tokens` 保留给旧布局兼容，不再控制新布局；新布局参数冲突不允许隐式覆盖。老任务由冻结配置选择旧 planner。

## 3. 实体目录：原始证据、合并条目、核心视图

### 原始层

保留节点抽取的 ENTITY 和引用。父节点 rollup 复制的子记录按原记录 ID/内容指纹消重，父子复制不当作新观察。名称仅做 Unicode/空白规范化；不擅自合并不同名字、不同版次和不同种类。事件、状态、时序、知情记录继续独立保留其披露范围。

### 完整合并目录

按“版本/分支 + 名称”分组，同名记录交给模型进行语义合并。共享前缀是截至当前可见位置的 L1 摘要；批次尽量装入多个完整名称组并预留输出。模型为一个名称保留简洁描述、译法差异、同名歧义、信息变化和来源成员 ID。程序检查所有输入成员恰好覆盖一次，名称不能由模型任意改写，来源不能编造。模型可保留同名歧义，不能把冲突强行消解。

单组过大时分批语义合并后继续归并，保存每一层中间结果。失败有界重试，保留已付费结果并返回明确状态；不得静默丢弃实体。原记录和完整出处留在存储，prompt 只携带紧凑描述和查询 ID。

初次处理所有可见名称组。每次增加 L1 后，用已有合并条目与新观察更新触及的名称组，不重复向模型发送全目录的原始记录；共享 L1 摘要包含新节点。依赖指纹支持幂等恢复。新建懒 L2 同样更新它涉及的名称组。

### 核心目录（默认上限 50 条）

完整目录不超过上限时直接使用，无额外核心筛选调用。超过上限才调用模型：公共前缀依次包含可见 L1 摘要、所选近距 L2 摘要、邻近原文（与已有中文参考），再给紧凑实体候选目录，要求返回至多 50 个已有实体 ID。先尝试在一个请求中比较完整候选目录；候选说明过长时逐级缩短说明，但不删除候选 ID。若全量列表仍超出预算，按实测请求预算拆批，每批保留同一前缀并为批次保留结果名额，再对入选并集作下一轮比较。若共享前缀本身放不下，则返回明确容量错误，不静默省略实体。

这一过程只选择 ID，不另写实体事实。解析器接受常见全角标点/代码围栏等格式变体，但不猜未知 ID；超限、重复或空清单触发有界重试。筛选依赖前缀与目录指纹，可复用完全相同的响应。需要拆批时，每批共享同一前缀且不靠固定截断丢掉候选；全量目录能装入一个请求时只需一次筛选调用。

核心视图进入翻译上下文时只携带名称、类别、简短描述、译法和候选状态等字段；描述最多 320 字符、最多 8 个译名（每个最多 80 字符）。长成员列表与证据摘录留在本地目录，按实体 ID 通过证据 API 查询，避免每轮重复注入全部出处。

当前目标正文中确切出现的非核心名称仍可定向召回；核心上限只限制长期常驻视图。其他实体仍可通过目录/证据接口查询。核心清单是模型选择的候选，并非权威事实。

### 非实体 workset

事件、状态、视角、时序和未决信息继续保留原始记录，但不再每条复制节点范围或长 ID。进入 prompt 的 workset 使用以下规则：

1. 按 `(type, fields)` 精确消重，合并父子节点副本；不对不同时间或不同人物认知做激进语义合并。
2. 记录使用 `K` + 8–10 个 base32 字符的稳定短 ID；完整 ID、节点修订和出处只保存在 `sequence-workset-catalog`。
3. prompt 字段做有界投影：描述最多 240 字符，引用最多 8 条，参与者/主体最多 8 条；完整字段通过短 ID 查询。
4. 相关性评分由目标章实体名的 IDF 加权命中、近期章节距离和记录类型共同决定；每类先保证少量近期记录，再按类型最低配额选取，最后按分数填满预算。
5. 默认 workset 预算 `workset_max_tokens = 128000`，近期窗口 `workset_recent_chapters = 25`；实体卡最多占可用预算的三分之一。
6. 未选记录保留短 ID 和分数。prompt 只带少量最高分未选 ID；完整目录可通过 `job.workset_catalog()` 查看，按短 ID 用 `job.knowledge_evidence()` 取回原始字段与出处。

v5 实测（185 章历史，128k 预算）：

```text
原始 workset            1,849,940 字符 / 约 2.18M 输入 tokens
压缩后 workset 消息        89,018 字符
整体检查点预计输入        271,370 tokens（上限 980,992）
选中知识记录             199 条 + 50 张实体卡
知识记录目标名命中          199 / 199
目标实体名覆盖              30 / 30
最近 10 章内记录            59 条
选中分数 min/median       34.30 / 50.77
```

未选记录中仍有一些高价值候选（最高分约 37.3），多为远距离未决 NEED 或与其他近期记录重复的视角/状态；它们保留在目录中，可按需查询。没有发现因去重而丢失的唯一重要记录。

### 未决线程整理

线程整理分为两级，避免每个 L2 都调用模型：

1. **L2 / 提交时：确定性筛选，不调用模型**
   - 从 NEED 创建稳定线程 `T...`；
   - 共享实体且问题字符 bigram Jaccard ≥ 0.62 的线程合并；
   - 按核心实体命中、重复次数、近期度计算 salience；
   - 低 salience 的 active 线程降为 `dormant`，不删除；
   - 后续实体再次出现时自动重新激活。
2. **L1 封口时：批量语义判定**
   - 只在 sealed L1（或冻结历史 L1）触发；
   - 候选包括 active 和与本 L1 相关的 dormant 线程；
   - 输入 L1 摘要、相关 L2 摘要、局部记录和紧凑线程卡；
   - 按 token 预算分批，每批 30–50 张卡；
   - 模型动作：resolved / partially_resolved / active / dormant / ambiguous / merge；
   - resolved/partial 必须有真实证据引用；合并只能指向同批线程；
   - 每批有独立缓存；失败的批次保留原状态。

workset 的接入方式：

- active/partially_resolved/ambiguous：固定进 workset；
- dormant：不固定，但实体命中当前目标时进入 `dormant_relevant` 摘要；
- resolved：从 selected NEED 移除，进入 resolved 摘要；
- merged/archived：不再作为候选；
- 线程摘要计入 workset 预算。

v5 L1 批量整理实测：

```text
历史 L1 节点                  2
候选线程                     47 / 67
每 L1 批次数                 1 / 1
模型更新                     6
确定性筛选前 active          173
筛选后 active               133
dormant                      40
merged                       0
resolved                     15
workset NEED                 44
workset 线程状态              active 31 / partial 12 / ambiguous 1
workset 预计输入              388,927 tokens（上限 980,992）
```

模型批量判定只解决了少量线程；真正降低 active 数量的是确定性 salience 筛选。这也说明不能只依赖一次模型调用做降级。

### 窗口并行翻译

公共入口：

```python
job.translate_window(size=None, concurrency=None, materialize=True)
```

- 窗口默认 `window_l2_blocks * child_max_chapters`，即 3 × 10 ≈ 30 章；
- 窗口开始前从日文和历史实体/译名目录预抽取新专词，冻结 batch glossary；
- 窗口内章节共享冻结 glossary 和窗口开始前的历史上下文，并行预翻译；
- 已知历史译名不得被改译；历史实体从全部 L1/L2 ENTITY 读取，并统一用 `t2s` 转成简体注入；
- 并行草稿只用于审校输入；按阅读顺序逐章审校/裁决/提交；
- 并行审校的 minor confirmed 记入 unresolved 后允许提交；审校协议/覆盖不完整或 confirmed critical/major 才回退到串行重审；
- 窗口全部提交后再统一 materialize，更新 L2/L1、实体目录和线程目录；
- 同一窗口内后续章节看不到前章新译文，窗口结束后需要术语/语气一致性检查。

2 章窗口试点：

```text
窗口章节                 2
预抽取术语               17
并行翻译完成             2 / 2
提交                     2
本轮请求                 18
本轮 prompt tokens       1,338,101
本轮 completion tokens   183,036
```

试点暴露并修复了一个重要问题：初版已知术语只读取了 selected workset 实体，导致已有的 `キーリ`、`アマゾネストレント`、`ガルデーニア` 被误当作新词，产生“琪莉 / 亞馬遜特倫特 / 加爾德尼亞”等不一致译名。现在已知术语来自全部历史 L1/L2 ENTITY，并用 `t2s` 统一注入简体。

## 4. 上下文与 API

- `index.plan()`：展示 token 布局、预检、短区间例外和需处理的容量诊断，本地调用不产生模型费用。
- `index.build_parent(..., method=None)`：默认采用计划的严格模式；显式方法可以选择二次摘要。未建 L2 不阻塞直接 L1。
- `index.entity_catalog(parent_id)`：本地读取原始实体，稳定消重，保留成员来源；独立版次实体匹配继续使用可追溯条目。
- `job.prepare_history()` / 译后增量：物化节点后构建/更新语义目录；超过阈值时准备核心视图。`plan_next()` 保持本地，无可用视图则明确返回待准备状态。
- `job.entity_catalog()`：读取完整合并目录的精简视图和核心选择状态，不返回长成员列表、全量来源清单或原文摘录；按条目 ID 用 `job.entity_evidence()` 取回出处。
- `job.workset_catalog()`：读取当前目标的 workset 选择摘要、预算、已选/未选短 ID 与类型计数，不返回完整记录。
- `job.knowledge_evidence(short_id)`：按 `K...` 短 ID 读取选中或未选的原始知识字段、节点范围和出处。
- `job.reconcile_threads()`：按封口 L2 顺序执行模型判定，可能产生调用；用于初始历史 backfill 或显式整理。
- `job.thread_catalog()` / `job.thread_evidence(thread_id)`：读取 active/resolved 线程、摘要、证据和最后出现位置。
- `config update` / `update_user_config()`：只允许修改非凭据字段，库内部读写完整配置，校验后原子替换，结果只返回字段名和配置状态；agent 不读取 API key。
- `cost_usage()`：返回持久请求数、预留输入/输出和已返回 usage。默认累计上限均为 0（无限制），单次容量与重试上限仍生效；0 不能被错误解释为没有预算。

## 5. 验证和交付

覆盖：token 偏斜、预期块数、30/100 边界、短书和尾部、严格模式阻断不调用模型、显式 rollup、正式 L2 不足 3 章、增量封口稳定、旧任务恢复；父子复制、同名差异/冲突、成员覆盖验证、语义合并的增量缓存、阈值内零筛选调用、超过 50 条的核心筛选、筛选上下文容量阻断、查询完整目录；0 无限预算但保留统计、安全配置更新不返回凭据。

先运行构造数据与离线 provider 的回归；必要的真实模型验证限制在小窗口，保存完整请求响应和费用，工程 complete 与语义正确分开报告。无需重建整本语料即可验证新行为。
